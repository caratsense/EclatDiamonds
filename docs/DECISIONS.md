| 2026-07-29 | **Delivery-readiness pass — silent no-op sends made honest, live gold rate, scheduled jobs** | One migration (`scheduled_job_runs`). Found while auditing whether the product could be handed to a client. **(1) The UI claimed sends that never happened.** Every external integration degrades to a logged no-op when credentials are absent — correct for a service, dangerous once the UI reads only the status code. `reporting/page.tsx` fired `toast.success("DSR sent over WhatsApp")` off a 200 regardless of the `delivered` flag, and the quote detail dialog's **"Share on WhatsApp" button made no request at all** — it only raised a success toast, so a rep could tell a customer at the counter that their price was on its way when nothing had been sent. Both now read the real outcome and distinguish delivered / not-connected / refused. New `ChannelStatusNotice` warns **before** a number is typed, driven by the existing `GET /integrations/status`, and disappears by itself once credentials are set. Also corrected "Quote created & shared" → "created" (nothing was shared). The two report dialogs were already honest and were left alone apart from the pre-emptive notice. **(2) New `POST /quotes/:id/share`.** Sharing a quote had to go through `POST /integrations/whatsapp/send`, which is manager-only precisely because it sends arbitrary text to an arbitrary number — so the salesperson who actually raises quotes would have got a 403. The new route derives the recipient **from the quote record**, so the caller chooses nothing: a rep can send a customer their own price without that also being a way to message anyone. Store-scope and the kaccha rule are inherited from `get()`. **(3) The quote builder was pricing off a hardcoded constant.** `autoRate` read `GOLD_RATE_PER_GRAM` from `lib/mock/quotation.ts` — ₹7,180/g for 22k, ₹5,920/g for 18k — and never called the rate API. Every "auto" quote was priced at whatever gold cost the day that file was written, which for a jeweller is a direct margin loss. Now wired to `GET /integrations/gold-rate`; the constant survives only as a last-resort fallback for a deployment with no `MetalRate` rows. `currentRates` additionally returns `effectiveFrom`/`ageHours`/`stale` (window via `GOLD_RATE_STALE_HOURS`, default 24h) and the builder labels the rate "today's rate", "out of date — last updated N days ago", or "no rate on record — using a built-in default". A stale rate and a fresh one look identical on the total; this is the only thing that distinguishes them. **(4) Scheduled jobs — nothing ran automatically before.** `POST /hrms/attendance/day-close` was built cron-friendly but there was no cron, so absence was only recorded if a manager remembered: a no-show left no row and payroll silently under-counted. New `SchedulerModule` ticks **hourly** rather than using one nightly cron, because cron expressions run on the SERVER's clock while attendance is store-local — `0 2 * * *` would close an Indian store at 07:30 local, mid-shift. Each tick asks every store what time it is *there* (`Store.timezone`) and fires only for the ones at the configured local hour (`DAY_CLOSE_HOUR`, default 02:00, late enough to clear night shifts). Adding a store in another zone needs no scheduler change. Also refreshes the gold rate hourly once a feed is configured. **(5) `ScheduledJobRun` + `JobRunnerService`.** `@Cron` fires inside *every* replica, so an in-process guard would not stop two instances closing the same day. Runs are claimed by INSERT against a unique `(job, scope, runKey)` index — first writer owns it, the loser gets P2002 and skips quietly. Chosen over a Postgres advisory lock, which is bound to the connection that took it and can be stranded by a crash under a pooled client. The table doubles as the answer to "did last night's close actually run?", which nothing recorded before; readable at `GET /scheduler/runs` (area+). A failing store is logged and skipped so one branch cannot stop the others closing. `SCHEDULER_ENABLED=false` disables the jobs on a clone without removing the module. **Verified:** 31 migrations apply clean from empty with zero drift; **20/20 new live assertions** (status honesty, salesperson CAN share a quote but still CANNOT send arbitrary messages, cross-branch share → 404, fresh rate not stale vs a 5-day-old rate flagged at 114.5h, run log gated to area+); **6/6 timezone assertions** proving a UTC-clocked server still fires each store on ITS 02:00 (and that the same instant is 20:00 UTC — what a naive cron would have used); day-close idempotency proven on an unclosed date (first run wrote 2 absences, second wrote 0); the duplicate-claim guard proven at the database (second INSERT rejected, a different store unaffected); **25/25 + 19/19 earlier assertions still pass**.
