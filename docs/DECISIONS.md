# 2026-09-07 — CRM Phase 2C: provider-backed AI drafting

- **Drafts only, and auto-send stays unimplemented.** `crmAiAutoSendEnabled` exists as a switch and nothing reads it to deliver anything. Approving a draft moves it to `queued`, exactly like a reply a person typed — never `sent`, which belongs to a transport that is not connected. WhatsApp's session-window and template rules have not been verified against live provider behaviour, and until they are, "sent" would be a lie the UI repeats to a salesperson.
- **Screening runs BEFORE the provider is called.** A complaint, an opt-out or a legal/regulatory mention never reaches a model: nothing is spent, no draft exists to be approved by mistake, and the customer's words are not handed to a third party in order to decide not to use them. The screen is keyword-based and deliberately blunt; every failure mode it has points at a person.
- **No knowledge, no draft.** If retrieval returns nothing, the assistant does not answer. A model with no material and a question in front of it is being invited to improvise, and "it only says what your documents say" has to be enforced, not merely instructed.
- **Confidence floor raised to 0.55** from 0.5. A coin-flip is not a standard for something a customer may read.
- **Customer messages and retrieved documents are both untrusted.** Both are fenced and labelled as data, and the fence markers are stripped from the content so it cannot forge an escape. Delimiters are one layer, not the control: the real controls are that output is never executed, never reaches a tool, and never leaves without a person reading it.
- **Provenance is a separate table** (`AiDraftRecord`), not columns on `Message`. Provider, model, confidence, latency, policy version and the knowledge document IDs are recorded, so "why did it say that?" is answerable later. Document IDs only — never the retrieved text, so deleting a document does not leave its content behind.
- **A policy version is stored on every draft.** Without it, changing a threshold makes every earlier draft unexplainable.
- **`edited` is recorded distinctly from `approved`.** "A person accepted it" and "a person had to rewrite it" are the two numbers that say whether the assistant is working.
- **A rejected draft is `rejected`, not `failed`.** A person declining and the network refusing are different facts; merging them would corrupt every delivery-failure metric.
- **Approval is `@HumansOnly()`.** Enforced by the guard, not by the observation that no machine currently calls it.
- **Retrieval is keyword-based, and that is a stated limitation.** `KnowledgeService.search` substring-matches the whole query, which returns nothing for a natural question — so the CRM side reduces the question to content words. Ranked/vector retrieval inside KnowledgeService is the real fix (REQ-005).

# 2026-09-08 — multi-market phase 2: entitlement is a server decision

- **Navigation visibility was never authorization, and now it is not asked to be.** `enabledNavigation` decided the sidebar and nothing else, so a clinic's manager who typed `/finance` got the page and `FinanceController` answered it — its only gate was a role check that manager satisfies. A single `EntitlementGuard` now runs beside `RolesGuard` and refuses the module itself. The two questions are different: `RolesGuard` asks "is this person senior enough", the industry gate asks "does this tenant's product include this at all".
- **A capability IS a navigation slug.** No second taxonomy was introduced. The pack already lists the routes an industry includes, so the menu and the API read one list and cannot drift. The mapping from request path to capability lives in `config/entitlements.ts` — one screen of code, testable without a server.
- **The map is allow-by-default, and that is deliberate.** Deny-by-default would make every unmapped controller — including ones another agent adds tomorrow — unreachable for everyone, turning a missing entry into an outage of a universal screen. The failure being prevented is narrow and enumerable; the failure invited by the opposite default is not. Tests pin the vertical list so a module cannot silently lose its entry.
- **Fail open on a request, fail closed on a write.** An unknown or absent pack is allowed through the request guard: locking a live tenant out of Finance because a deploy shipped without their pack definition is worse than the leak. The hourly metal-rate job takes the opposite default — a tenant we cannot classify simply stops accruing gold prices, which costs them nothing.
- **The neutral product columns are the fix for stored data, not a label.** A clinic's every product was *stored* as a 22K gold necklace, because `metal` is a required enum whose form default was submitted whether or not anyone saw the control. Hiding the field is what lets `unspecified` / `other` be sent, with the tenant's real words in `categoryLabel` / `materialLabel` / `unitOfMeasure`. Relabelling could never have reached this.
- **Industry switching converges the funnel, tracked explicitly rather than guessed.** Every pack ships pipeline code `default` with the same three stage codes, so insert-only provisioning left a tenant on the previous industry's wording for ever. `Pipeline`/`PipelineStage` carry no `packCode` column (and this phase could not add one), so `Organisation.settings.packManaged` records the exact strings the last apply wrote. A row still equal to that record is the pack's to correct; anything else is the tenant's. A tenant with no record — everyone provisioned before this — is treated as tenant-owned and never rewritten.
- **Convergence relabels; it never deletes.** A stage the previous pack seeded that the new one does not ask for is left in place, because a lead may be standing in it. `outcome` and `systemValue` are never rewritten either — reports read those, so touching them would change historical conversion numbers.
- **One row lock replaced three lost updates.** `Organisation.settings` is one JSON column shared by unrelated features, and three services each read it whole, spread it, and wrote it back — so turning the AI assistant on could silently delete a tenant's ad-set routing rules, with both requests returning success. `updateOrgSettings` takes `SELECT … FOR UPDATE` first. A `jsonb ||` merge would have been shorter and fixes two of the three; it cannot fix the qualification policy, whose `version: current.version + 1` must be read before it is written.
- **Signup no longer confirms whether an email exists in another tenant.** `/auth/login` deliberately returns one message for a bad email and a bad password; the public create-organisation route was the hole in the same wall, answering precisely for any address on the platform.
- **Qualification is left OFF at signup**, matching `DEFAULT_QUALIFICATION_POLICY` and the comment beside it. A brand-new tenant is exactly the case that comment is about: nobody has read the policy and no knowledge exists for it to score against.
- **Branding is the tenant's name, not an uploaded asset.** Eclat keeps its own artwork, identified by organisation slug; everyone else sees their own name set in the product face. Logo upload and storage were explicitly not built — the name is something signup already knows, so it can be shown honestly today without an asset pipeline. The sign-in screen is neutral because it is shared and pre-tenant.

# 2026-09-15 — store-scoped self-signup and Login IDs

- **Applicants request salesperson or storeperson.** Store manager self-request is off unless head office turns on `signupPolicy.allowManagerSelfRequest`, and a manager-level request is approved by head office only (the folded area tier included). Pending manager requests made before this stay approvable by head office.
- **A Login ID is an identifier, not a mailbox.** New IDs follow `signupPolicy.loginIdTemplate` (tokens `{firstname}`, `{lastname}`, `{storeslug}`, `{orgslug}`) or, when unset, the existing default. The part after "@" must carry the tenant's own code or `{orgslug}` (or be its existing default domain), because `User.email` is unique across tenants and sign-in has no tenant context. Stored IDs, including legacy `@eclatdiamonds.in` and seeded `@caratsense.in`, are never rewritten.
- **The unique index assigns the ID.** Writes retry on a unique violation with the next suffix; inside the approval transaction each attempt runs in a savepoint. The public preview renders the template only and reads no user rows.
- **Approval is one transaction with a conditional claim** on `approvalStatus = 'pending'`: approver role and scope re-read from the database, the store must be open, and binding + re-issued ID + audit + applicant notification commit together; a replay or race gets 409. The approval email is sent after commit and reported as sent / dry_run / failed / no_contact_email.
- **Reapplication: a rejection is terminal for the request, not the person.** The rejected row can never be approved or activated; the person may send a fresh request at any time (new row, new Login ID) and the approver sees the latest earlier decline for that phone. No public cooldown: phone is optional (so a cooldown is bypassable) and a distinct refusal would reveal whether a number was declined. The per-IP signup throttle bounds spam.

# 2026-09-18 — attendance: employee master, punch ledger, EzAttendance import

- **Personal columns (DOB, blood group, address) are redacted below head office in the employee API and never written to audit metadata.**
- **An employee is a User with an EmployeeProfile beside it, never a second person.** Department and designation are masters with stable ids; "Bandra" and "BANDRA" import as one row, and the source row is kept verbatim in `sourceRaw`.
- **Raw punches are append-only.** A correction is a new `RawPunchEvent` (source manager/regularization) or a void flag, never an edit; the daily register is computed from them and can be reprocessed.
- **Head office may correct and delete attendance rows**, with a mandatory reason and audit. This narrows the earlier "HO is observe-only": HO still does not punch for others from the mark dialog.
- **A locked payroll month refuses attendance, leave and punch writes** until head office reopens it with a reason.
- **One eligible-employee rule and one day classification** feed Today, day-close, processing and every report, so dashboard, register and payroll totals reconcile. Late is a modifier of present, never an extra person.
- **A confident check-in fix outside a configured fence is refused**, note or not. An uncertain or missing fix still records with a reason for review; check-out stays lenient.
- **EzAttendance leave "E" is earned leave; "K" is imported as `week_off_leave`.** K is ~53 days a year and is held only by store staff with no weekly-off rule, i.e. their one off day a week taken as leave. To be confirmed with the client.
- **Idle time ends the app session, not the working day.** Browser inactivity is not evidence someone left work, so it no longer checks the employee out.
- **The "face verified" logout path is removed.** A captured frame is evidence, not identity verification; real enrolment/liveness needs a vendor and is not built.
- **Working and signing in are separate.** Imported staff arrive without a login (User inactive) but are counted for attendance by their EmployeeProfile status; `User.isActive` decides only whether they can sign in.
- **A flexible shift never produces "late"**, even where EzAttendance flagged it (its "F" shift starts at 05:00, which made every F employee hours late).
- **Imported punch keys are namespaced by organisation** (`ezatt:<orgId>:<code>:<date>:in`), since the idempotency column is unique across tenants.
- **Attendance rate = (present + half day) ÷ (present + half day + absent + not marked).** Week-offs, holidays and leave do not lower it. Payable days follow `PayrollService.countDays` (attended days earn their day fraction; leave, week-off and holiday are paid).
- **Personal columns (DOB, blood group, address) are head-office only** in every report; below head office birthdays show day and month only.
- **A day is derived from its live punches: first `in`, last `out`.** An `out` belongs to the day whose first `in` precedes it by under 24 h (night batches), else to its own date. A correction (register edit, manager mark, approved regularization) VOIDS the punches it replaces on that side and appends its own, so a processing run reproduces exactly what the correction showed. A register row written before the ledger existed has its times appended as `backfill:` punches the first time its day is reprocessed, so a run never erases history.
- **Processing never overrules a human non-attended mark.** With no live punches, a manager/import/regularization `absent`/`on_leave`/`week_off`/`holiday` row stands; `auto` rows are reclassified (leave > holiday > week off > absent); today is never written absent.
- **No self or peer attendance correction:** a manager cannot mark, edit, delete or punch for themselves or anyone at or above their rank; head office corrects anyone but itself. The same rule covers editing/deleting someone's leave and their shift assignments.

# 2026-09-18 — attendance is dashboard-native, not terminal-dependent

- **CaratOS is the attendance system of record.** Employees check in and out through the authenticated dashboard/mobile web app; managers review and correct records in the same product. A biometric terminal, vendor cloud, or desktop attendance agent is not required for normal operation.
- **A camera frame is optional evidence, never authentication.** The product must not call a locally stored photograph “face enrolled”, “face verified”, or use it to bypass credentials. Genuine face matching/liveness and external biometric-device sync are out of scope unless separately contracted later.
- **Location policy is enforced by the server.** A precise out-of-fence check-in is refused; unavailable or inconclusive GPS needs a written reason and review; an out-of-fence checkout needs a reason. Browser-local grace counters must never decide attendance.
- **Legacy identifiers are archival only.** Imported biometric numbers may be retained as “legacy attendance IDs” for reconciliation, but no dashboard workflow depends on a device being connected.
- **A flexible shift with no explicit `fullDayMins` credits a worked day like "no shift"** (any time worked = 1), because its 05:00-23:00 window is when one may work, not a length to fill.

### Visual index + search (Module 5, 2026-09-18)
- **Indexing is a durable JobTask per picture** (`catalogue.embed_image`, key = org + image + contentHash-or-url + pipeline version, priority -1). `ProductImage.embeddingStatus` is the only progress truth; `POST /products/embeddings/reindex` queues, `GET` returns DB counts. No in-memory runs, no 5,000 cap. A permanent failure (404, not an image, host not allowed, too large) marks the picture `dead` immediately; transient ones retry with the queue's backoff and are `dead` after 5 attempts.
- **Downloads are allow-listed**: own `/uploads`, `data:` URLs, the R2 public host, Cloudinary when configured, and `CATALOGUE_IMAGE_ALLOWED_HOSTS`. Redirects are re-checked per hop; size cap `CATALOGUE_IMAGE_MAX_BYTES` (15 MB); type from magic bytes only.
- **Enqueue never calls inference** (it uses the last version it saw). The worker stamps the real version; a 10-minute sweep re-queues `pending` pictures and anything indexed under an older version, and deletes vectors of tombstoned pictures (the syncs tombstone without telling the index). Search ignores non-active pictures regardless.
- **Thumbnails come from the inference service** (`thumbnail_px` → `thumb_b64`), with no image library added to the backend. Until the service supports that, `thumbUrl` stays null.
- **Search**: returns `CATALOGUE_INDEX_BUILD_REQUIRED` with coverage before calling inference; makes one `/embed/batch` call per search; allows `SEARCH_MAX_CONCURRENT` (2) searches per instance, else 429 + Retry-After; caches query vectors (LRU 64, 10 min) by image sha256; has one deadline, `SEARCH_DEADLINE_MS` (45 s); sends a Server-Timing header, with p50/p95 in the status response.
- **pgvector is optional**: migration `20260918160000_pgvector_ann_768` adds partial expression HNSW indexes over the existing Float[] columns (768 dims, no new columns). It does nothing if the extension is missing; re-run it by hand if pgvector is installed later. ANN is used only with `SEARCH_PGVECTOR=1` and when both indexes are found at boot. The 1024/1152 drafts in `prisma/manual` stay unapplied.
