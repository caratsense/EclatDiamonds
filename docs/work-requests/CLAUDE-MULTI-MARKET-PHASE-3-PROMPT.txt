Pipeline pack ownership (MM2-03). Raised BEFORE the edit, per the fence.

WHAT I AM ABOUT TO CHANGE
  backend/prisma/schema.prisma          two nullable columns, no other edit
  backend/prisma/migrations/20260908190000_pipeline_pack_ownership/migration.sql

COLUMNS (both nullable, both mirroring the existing TaxonomyTerm /
AttributeDefinition / FieldPolicy convention exactly)

  model Pipeline      { packCode String?   @@index([organisationId, packCode]) }
  model PipelineStage { packCode String?   @@index([organisationId, packCode]) }

NULL means tenant-owned. A non-null value is the pack code that last wrote the
row, and is the ONLY licence provisioning has to re-word it.

MIGRATION (additive; no drop, no type change, no NOT NULL, no default)

  ALTER TABLE "Pipeline"      ADD COLUMN "packCode" TEXT;
  ALTER TABLE "PipelineStage" ADD COLUMN "packCode" TEXT;
  CREATE INDEX "Pipeline_organisationId_packCode_idx"      ON "Pipeline"("organisationId","packCode");
  CREATE INDEX "PipelineStage_organisationId_packCode_idx" ON "PipelineStage"("organisationId","packCode");

BACKFILL — evidence only, never a name guess

Phase 2 recorded what the pack actually wrote in
Organisation.settings.packManaged.pipeline = { code, name, stages: {code:label} }.
A row is stamped ONLY when it still equals that record:

  Pipeline      <- packManaged.packCode  where code = record.code
                                           AND name = record.name
  PipelineStage <- packManaged.packCode  where label = record.stages[stage.code]

Everything else keeps packCode NULL and stays tenant-owned, including every
organisation with no packManaged record at all (Eclat among them — its funnel is
never touched by this).

Then, in the SAME transaction and only for rows the stamp succeeded on, the now
redundant `pipeline` key is removed from packManaged. `qualificationPrompts`
STAYS: question ownership still has no column, and dropping it would hand every
tenant's reworded questions back to the pack.

WHY IT CANNOT WAIT FOR A COLUMN-FREE FIX
Ownership in JSON cannot survive a tenant renaming the pipeline and cannot be
indexed or joined; MM2-04 additionally needs to stamp rows created by
ensureDefault, which has no settings record of its own to write into.

If this collides with a concurrent schema edit, this migration is standalone:
re-generating it against the settled schema needs no other file changed.
