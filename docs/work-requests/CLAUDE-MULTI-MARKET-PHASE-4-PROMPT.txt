MM4-01  Every tenant's stock-transfer dialog lists ECLAT's branches.     HIGH
        Owner: frontend/src/lib/queries/auth.ts
               frontend/src/components/inventory/create-transfer-dialog.tsx
--------------------------------------------------------------------------------
    auth.ts:90    export function useSignupStores(organisationCode = "eclat") {
    dialog.tsx:70   const { data: stores = [] } = useSignupStores();
    dialog.tsx:141  const destinations = stores.filter((s) => s.id !== sourceStoreId);

The hook defaults its tenant to the literal "eclat"; the transfer dialog calls it
with no argument. So `destinations` — the "transfer to" picker — is populated
from Eclat's PUBLIC store directory for whoever is signed in.

This is not only a display leak. The picker offers another organisation's branch
ids as selectable destinations for a stock transfer. The server's store-scope
check should refuse the submission, so the likely outcome is a confusing failure
rather than a cross-tenant write — but the UI is naming a stranger's branches as
valid choices, and it is one server-side gap away from being worse.

Today only a tenant with the `stock-transfers` capability reaches this screen,
which post-phase-3 means Eclat and any future jewellery tenant. The second
jewellery customer to sign up is the one who sees it.

Requested: delete the `= "eclat"` default so the argument is required, and pass
the signed-in organisation at the call site. A tenant identity should never have
a fallback; absent, it is a bug, not a default.

MM4-02  A local `docker build` bakes the production backend, unfixably.  MEDIUM
        Owner: frontend/Dockerfile
--------------------------------------------------------------------------------
The Dockerfile declares `ARG NEXT_PUBLIC_API_URL` but no `ARG BACKEND_ORIGIN`.
Since next.config.ts resolves rewrites() at build time, the image's
routes-manifest is frozen with the production Railway default, and
`docker run -e BACKEND_ORIGIN=…` is inert against it. `.dockerignore` excludes
`.env*`, so a corrected env file never enters the build context either.

The phase-4 preflight cannot see this: it reads the host filesystem, not the
inside of an image. Requested: `ARG BACKEND_ORIGIN` + `ENV` before the build
step, mirroring how NEXT_PUBLIC_API_URL is already handled.
