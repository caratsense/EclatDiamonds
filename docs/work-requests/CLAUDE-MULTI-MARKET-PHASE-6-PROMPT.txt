SF-06  schema.prisma + industry-packs/packs.ts — LeadSource.meta_ads
Status: REQUESTED -> APPLIED (INT-03), 2026-09-09
Owner:  shared (schema is edited by three agents; packs.ts by the
        multi-market lane)
--------------------------------------------------------------------

WHY
A lead harvested from a Facebook or Instagram Lead Ad form has no honest member
of the closed `LeadSource` enum. `instagram` is wrong for a Facebook form and
right for neither in general; `website` is a lie; `whatsapp` is the channel the
reply happens on, not where the lead came from. Storing Meta leads under any of
them poisons every source-mix report and every saved segment that filters on
sources, and it is not reversible once written.

WHAT
1. schema.prisma — ONE value appended to the LeadSource enum:

     enum LeadSource { walk_in phone whatsapp website instagram referral
                       meta_ads }        <- appended, nothing reordered

   No existing value is renamed, reordered or removed. Appending is the only
   safe operation on a Postgres enum with data in it.

2. industry-packs/packs.ts — one term appended to the shared LEAD_SOURCE
   taxonomy constant. All five pack definitions reference that one constant, so
   every industry pack mirrors the new source without five separate edits.

     { code: 'meta_ads', label: 'Meta Ads', systemValue: 'meta_ads',
       sortOrder: 7 }

MIGRATION
  20260909150000_lead_source_meta_ads — a single ALTER TYPE ... ADD VALUE.
  Additive and forward-only. No DROP, no DELETE, no type narrowing, no
  backfill: nothing is relabelled, because no existing row carries deterministic
  evidence that it came from a Meta lead ad. An `instagram` lead stays
  `instagram`. Inventing provenance to populate a new value would be worse than
  leaving history as it is.

IDEMPOTENCY / TENANT SAFETY
  Pack provisioning already looks up each term by (organisationId, kind, code)
  and SKIPS any that exists (provision.ts:71-84), so:
    - re-running provisioning creates the term at most once per tenant;
    - a tenant who relabelled or hid a lead-source term keeps their version;
    - existing tenants pick the term up on their next pack application.

  The migration is guarded so re-running it is safe on a database that already
  has the value.

RISK
  Low. The one thing to know: Postgres cannot use a newly added enum value in
  the same transaction that adds it. This migration only ADDS the value; the
  first row written with it comes from a later request, so that restriction is
  never hit.

SF-10  schema.prisma -- AuditLog gains a third actor identity
Status: REQUESTED -> APPLIED (INT-11), 2026-09-09
--------------------------------------------------------------------

WHY
Some decisions have no person and no Connect agent behind them: an inbound
webhook placing a lead in the round-robin queue, a public QR form creating one.
Ownership genuinely changes hands. With only two actor columns and a database
CHECK requiring exactly one of them, the code's only options were to fake a
human actor or write nothing -- and it wrote nothing (advanced-crm.service.ts
had `if (actor)` around the audit call).

WHAT
  systemActorId String?   on AuditLog, plus @@index([systemActorId])
  The CHECK is REPLACED, not weakened:
      num_nonnulls("actorId","machineActorId")               = 1
   -> num_nonnulls("actorId","machineActorId","systemActorId") = 1
  So a row with no actor at all remains impossible.

  common/audit.service.ts gains SYSTEM_ACTORS (a closed list of automations)
  and recordSystem(). audit-read.service.ts reports a third actorType,
  'system', instead of rendering such a row as a user with a null id.

MIGRATION
  20260909180000_audit_system_actor
  ADD COLUMN IF NOT EXISTS, DROP CONSTRAINT IF EXISTS, ADD CONSTRAINT,
  CREATE INDEX IF NOT EXISTS. Every existing row already names exactly one of
  the first two identities, so the new constraint validates without touching
  data.

RISK
  Low, with one thing to know: replacing a CHECK takes a brief ACCESS EXCLUSIVE
  lock on AuditLog while Postgres validates it. On a large trail, run it in a
  maintenance window or split it into ADD CONSTRAINT NOT VALID + VALIDATE.

SF-11  schema.prisma -- AdSpendDaily and AdSpendCoverage
Status: REQUESTED -> APPLIED (INT-05/06), 2026-09-09
--------------------------------------------------------------------

WHY
Provider-measured advertising spend was stored as JSON in LegacyRow, the untyped
table the import pipeline stages raw source rows in. As a home for money that
fails three ways: a JSON string cannot be a Decimal, nothing constrains the
currency, and the only key is a composed rowKey string, so the database cannot
tell a replay from a second genuine row. Reporting re-validated every blob on
read and SILENTLY DROPPED the ones that failed -- which is how a ROAS
denominator shrinks without anyone noticing.

WHAT -- two new tables. No existing table is altered.
  AdSpendDaily     one campaign, one ad account, one account-local day
                   spend Decimal(18,4), currency with a CHECK ~ '^[A-Z]{3}$',
                   @@unique([organisationId, adAccountAssetId, date,
                             externalCampaignId])  <- the replay guard
  AdSpendCoverage  proof that a day was fully ingested, kept apart from the
                   spend rows because "no spend on Tuesday" and "Tuesday was
                   never fetched" are different facts

  Back-relations added to Organisation and Integration.

MIGRATION
  20260909190000_ad_spend_measured_models
  CREATE TABLE IF NOT EXISTS x2, unique + reporting indexes, currency and
  non-negative CHECKs, foreign keys. Purely additive.

BACKFILL
  backend/scripts/backfill-ad-spend.mjs -- dry run by default, --apply writes.
  Idempotent (every write is an upsert on the natural key), non-destructive
  (the LegacyRow blobs stay), and it REPORTS the rows it could not read with
  their source table and row key rather than coercing them to zero.

RISK
  Low. Old LegacyRow blobs are left in place, so the backfill can be re-run and
  the previous data is still there if the new path has to be re-derived.
