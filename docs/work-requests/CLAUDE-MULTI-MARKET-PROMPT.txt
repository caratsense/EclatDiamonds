--------------------------------------------------------------------------------
MM-01  Module entitlement is not enforced anywhere.            SEVERITY: HIGH
        Owner: backend/src/auth/** + backend/src/common/** + frontend layout
--------------------------------------------------------------------------------
`enabledNavigation` is consulted by four components (sidebar, mobile nav, and
now the gold-rate chip and the welcome tour). There is no route guard in
frontend/src/app/(app)/layout.tsx, no middleware.ts anywhere, and no backend
guard: a grep for enabledNavigation / industryPackCode across backend/src
returns only auth/auth.service.ts and config/*.

So a pharmacy's store manager who types /finance still gets the page, and
FinanceController answers it — its whole gate is
@Roles('store_manager','head_office'). The industry layer currently hides
doors; it does not lock them.

Requested: a pack-aware guard alongside RolesGuard, registered in app.module.ts,
plus a client-side route check. Claude cannot add either — auth/, common/ and
app.module.ts are all outside the fence.

Related, same area: GET /integrations/gold-rate (integrations.controller.ts,
around line 166) carries NO @Roles decorator at all.


--------------------------------------------------------------------------------
MM-02  The product form writes jewellery data for every tenant. SEVERITY: HIGH
        Owner: catalogue implementation (held) + prisma/schema.prisma
--------------------------------------------------------------------------------
The most consequential finding, and a DATA problem rather than a labelling one,
so no amount of relabelling reaches it.

frontend/src/app/(app)/catalogue/page.tsx defaults a new product to category
'necklace' and metal 'gold_22k'. Both are required by CreateProductDto, and
Product.metal is NOT NULL with no industry-neutral member in enum MetalKind.

Result: every product a pharmacy, clinic or factory creates is STORED as a 22K
gold necklace. The comment in packs.ts promising that non-jewellery categories
"map to `other` at the column" is not true of the write path.

Requested:
  a) an industry-neutral option for Product.metal — nullable, or an `na` member
     — in schema.prisma plus a migration and products/dto/product.dto.ts;
  b) the create form defaulting to it.


--------------------------------------------------------------------------------
MM-03  FieldPolicy is provisioned and never honoured.           SEVERITY: HIGH
        Owner: catalogue implementation (held)
--------------------------------------------------------------------------------
Every non-jewellery pack writes FieldPolicy rows hiding product.purity,
grossWeight, netWeight, makingChargeType and huid. The reader that would apply
them, useFieldVisible in frontend/src/lib/queries/tenant-config.ts, has ZERO
call sites repo-wide. Nothing on the backend enforces them either.

So the Add Product dialog still renders Karat and Gross wt (g), and
ProductDetailDialog still renders Purity, Gross weight, Stones (ct) and
Hallmark, for every tenant. The pack comment "a pharmacist never sees an empty
karat box" is currently false.

Requested: call useFieldVisible in catalogue/page.tsx (the metal select, karat,
gross weight, and their validation branches) and in
components/catalogue/product-detail-dialog.tsx (the spec rows).

NOTE FOR HONESTY: backend/test/industry-onboarding.e2e-spec.ts asserts that
these hidden rows are written. That assertion is true about the database and
says nothing about the screen. It is not evidence the fields are hidden.

MM-11  The full e2e suite cannot pass on a freshly seeded DB.   SEVERITY: MEDIUM
        Owner: prisma/seed.mjs + backend/src/discounts/**
--------------------------------------------------------------------------------
Found while running the full regression for this work. Pre-existing, unrelated
to the product layer, and reproducible on any fresh seeded database.

prisma/seed.mjs hardcodes two discount requests with ref "DR-1001" and
"DR-1002" (seed.mjs:423,432). discounts.service.ts:196 generates its ref as
`DR-${1000 + seq}` from SequenceService.next('DR:global'), and the seed never
advances that sequence — so the first discount created through the API asks for
"DR-1001" and hits the unique constraint.

Effect: app.e2e-spec.ts "Discount ceilings + mass-assignment guard (M15)" fails
both of its cases with a 500 (Unique constraint failed on the fields: (`ref`)).
That is 2 of the 559 tests in the suite.

Fix is either end: have the seed advance 'DR:global' past the rows it writes, or
have the seed use refs the sequence will never mint. Claude did not change it —
both files are outside the fence for this task.
